# Шаблон репозитория: Разработка информационной системы

Стартовый шаблон для быстрой инициализации проектов на .NET 10 с настроенным контролем качества кода, автоматизацией и генерацией документации.

Этот репозиторий содержит полностью готовую инфраструктуру: от правил статического анализа и pre-commit хуков до автоматического деплоя документации на GitHub Pages. Он позволяет сразу сосредоточиться на бизнес-логике, заменив шаблонные имена на названия вашей предметной области.

---

## Для чего этот репозиторий

Данный репозиторий является стартовым шаблоном (template) для быстрой инициализации новых проектов. Основное назначение — разработка информационной системы по теме, которую вы выберете при создании репозитория.

Шаблон включает в себя полностью настроенную инфраструктуру, строгие процессы обеспечения качества кода, автоматизацию проверок и генерацию документации. Это позволяет не тратить время на рутинную настройку окружения, а сразу приступить к реализации бизнес-логики.

---

## Технологический стек

- Платформа: .NET 10 (версия SDK зафиксирована в `global.json`), C# 14.
- Веб-фреймворк: ASP.NET Core Web API.
- Документирование API: Scalar (современная альтернатива Swagger UI).
- Тестирование: NUnit + coverlet (сборка покрытия кода).
- Контроль качества: `dotnet format` (встроенное форматирование), Roslyn-анализаторы (Meziantou, SonarAnalyzer, StyleCop), строгий `.editorconfig`.
- Документация и визуализация: Doxygen + Mermaid (`.mmd`) с автоматической публикацией на GitHub Pages.
- Орфография: CSpell с поддержкой русского, английского и технических словарей.
- Автоматизация: Husky.Net (pre-commit хуки), GitHub Actions (CI/CD), Central Package Management.

## Что установить локально

Для комфортной работы с шаблоном на вашей машине должны быть установлены:

1. Git — система контроля версий.
2. .NET SDK 10.x — версия подтянется автоматически из `global.json`.
3. Node.js 22+ и npm — необходимы для работы CSpell, Mermaid CLI и Husky.
4. IDE (Visual Studio 2026 / JetBrains Rider / VS Code) — с включенной поддержкой `.editorconfig`.

После клонирования репозитория выполните в корне:

    # 1. Восстановление NuGet-пакетов
	```bash
    dotnet restore
	```

    # 2. Восстановление локальных инструментов .NET (Husky)
	```bash
    dotnet tool restore
	```

    # 3. Установка зависимостей Node.js
	```bash
    npm install
	```

    # 4. Активация pre-commit хуков
	```bash
    dotnet husky install
	```

## Что изменить под себя (обязательно)

Поскольку это шаблон, в нескольких конфигурационных файлах жестко прописаны имена `Library`, `API` и `Domain`. Перед началом разработки их необходимо заменить на названия вашего проекта.

### 1. Переименование решения и проектов

- Переименуйте файл `sources/Library.slnx` в `sources/ВашеРешение.slnx`.
- Переименуйте папки проектов (`API`, `Domain`, `Domain.Tests`) и файлы `.csproj` внутри них под вашу предметную область.
- Обновите пространства имен (`namespace`) в файлах `.cs`.
- Обновите ссылки между проектами (например, в `Domain.Tests.csproj` путь к `Domain.csproj`).

### 2. Обновление конфигурационных файлов

После переименования обязательно откройте и исправьте следующие файлы:

- `task-runner.json`: в аргументах команды `format` замените `sources/Library.slnx` на `sources/ВашеРешение.slnx`.
- `.github/workflows/dotnet.yml`: в секции `env` замените `SOLUTION: Library.slnx` на `SOLUTION: ВашеРешение.slnx`.
- `.github/workflows/docs.yml`: в секции `paths` замените `sources/Domain/` и `sources/API/` на пути к вашим новым проектам (иначе документация не будет пересобираться при их изменении).
- `sources/_stylecop/stylecop.json`: при необходимости обновите `copyrightText`.
- `docs/Doxyfile`: замените `PROJECT_NAME` на название вашего проекта.

### 3. Адаптация словарей

- Отредактируйте файлы в папке `dics/` (`ru.txt`, `en.txt`, `tech.txt`), добавив специфичные для вашей предметной области термины и удалив шаблонные.

## Использование

После адаптации шаблон полностью готов к работе:

- Любая попытка сделать коммит с неформатированным кодом будет автоматически отклонена хуком `dotnet format`.
- При пуше в ветку `master` автоматически запускается сборка, тесты и проверка стиля (файл `.github/workflows/dotnet.yml`).
- При изменении кода или документации автоматически генерируется и публикуется сайт с документацией (файл `.github/workflows/docs.yml`).

### Настройка GitHub Pages (сделать один раз)

1. Перейти в Settings -> Pages -> Build and deployment.
2. В поле Source выбрать GitHub Actions.
3. Остальное создастся автоматически при первом успешном запуске workflow.

URL сайта будет виден в логах шага Deploy to GitHub Pages (формат: `https://<owner>.github.io/<repository>/`).

### Окончания строк

Файл `.gitattributes` жестко предписывает использовать окончания строк `LF` для всех текстовых файлов. Рекомендуемая настройка клиента Git: `git config --global core.autocrlf false`.

## Контроль качества кода

В проекте выстроена строгая культура написания кода. Все проверки запускаются автоматически.

### Локально (pre-commit хуки)

Перед каждым коммитом Husky.Net автоматически запускает задачу из `task-runner.json`:

    dotnet format sources/ВашеРешение.slnx

Если код не соответствует `.editorconfig`, коммит будет отклонен, а файлы автоматически отформатированы.

### В CI (GitHub Actions)

Все проверки дублируются в пайплайне `.github/workflows/dotnet.yml`:

- Восстановление локальных инструментов (`dotnet tool restore`).
- Проверка формата кода (`dotnet format --verify-no-changes`).
- Восстановление зависимостей (`dotnet restore`).
- Сборка решения в режиме Release.
- Запуск тестов с генерацией покрытия.

### Статический анализ

Используется многоуровневая система анализаторов:

- `Directory.Build.props` (в корне) — включает .NET анализаторы, устанавливает уровень `latest-recommended`, принудительно применяет стиль кода при сборке, генерирует XML-документацию для Swagger/Scalar.
- `.editorconfig` (в корне) — строгие правила стиля: обязательное использование `this.`, `var` только для встроенных типов, `using` внутри namespace, фигурные скобки в стиле Allman, приватные поля в camelCase без подчеркивания.
- `.globalconfig` — глобальные переопределения серьезности конкретных диагностик (например, отключение предупреждений о TODO, локализации, упрощении коллекций).
- `sources/_stylecop/develop.ruleset` — набор правил StyleCop для основного кода.

### Особенности для тестов

К тестам применяются ослабленные требования, чтобы не отвлекать разработчиков от сути тестов. Это реализовано через два файла в папке `sources/tests/`:

- `tests/Directory.Build.props` — импортирует корневой `Directory.Build.props`, но переопределяет:
    - `IsTestProject = true`
    - `TreatWarningsAsErrors = false`
    - `GenerateDocumentationFile = false` (XML-документация в тестах не нужна)
    - Использует `tests.ruleset` вместо `develop.ruleset`
- `tests/.editorconfig` — переопределяет правила только для тестов:
    - `csharp_style_var_elsewhere = true:suggestion` (можно использовать `var` везде)
    - `dotnet_diagnostic.CA1707.severity = none` (можно использовать подчеркивания в именах методов тестов, например `Should_Return_True_When_Input_Is_Valid`)

Благодаря этому тесты остаются читаемыми и не загромождаются лишней документацией, а основной код сохраняет строгий стиль.

## Документация и GitHub Pages

Документация генерируется через Doxygen и публикуется на GitHub Pages автоматически через workflow `.github/workflows/docs.yml`.

### Когда запускается сборка

Workflow срабатывает только в трёх случаях:

1. Push или мерж в `master`, если изменились файлы из списка: `sources/Domain/`, `sources/API/`, `docs/`, `dics/`, `.cspell.json`, `.github/workflows/docs.yml`, `package.json`.
2. Публикация GitHub Release.
3. Вручную через кнопку Run workflow во вкладке Actions.

Важно: отдельных триггеров на `pull_request` нет. При открытии или обновлении PR документация не публикуется. Сборка происходит только после мержа в `master`.

### Проверка орфографии (CSpell)

Перед генерацией запускается проверка орфографии. Для гарантированной работы словарей в CI:

- Устанавливаются пакеты, указанные в `package.json` (включая `@cspell/dict-ru_ru` и `@cspell/dict-en_us`).
- Конфигурация берётся из `.cspell.json`, который подключает стандартные словари (`ru-ru`, `en-us`, `russian`, `english`) и пользовательские словари из папки `dics/` (`project-ru`, `project-en`, `project-tech`).

## Как обновлять версии

### Обновление .NET и NuGet-пакетов

- Версия SDK: измените номер в `global.json`.
- Версии пакетов: измените версии в `Directory.Packages.props`. Благодаря Central Package Management, вам не нужно менять версии в каждом `.csproj` файле.

### Обновление Node.js зависимостей (CSpell, Mermaid)

Версии инструментов зафиксированы в корневом `package.json` с использованием символа `^` (caret):

    {
      "devDependencies": {
        "cspell": "^8.0.0",
        "@mermaid-js/mermaid-cli": "^10.9.0",
        "@cspell/dict-ru_ru": "^2.0.0",
        "@cspell/dict-en_us": "^4.0.0"
      }
    }

Правило `^`:

- Патчи (8.0.1) и минорные (8.1.0) версии подхватываются автоматически при `npm install`.
- Мажорные (9.0.0) версии не подхватываются, что защищает сборку от внезапных поломок API.

Файл `package-lock.json` не коммитится (добавлен в `.gitignore` вместе с `node_modules/`). В workflow намеренно отключен `cache: 'npm'`, чтобы зависимости устанавливались чисто и предсказуемо при каждом запуске.

#### Как обновить мажорную версию вручную

1. В `package.json` поменяйте версию, например: `"cspell": "^9.0.0"`.
2. Закоммитьте изменение и оформите PR в `master`.
3. После мержа workflow соберёт документацию с новой версией (изменение `package.json` есть в триггерах).

Примечание: LTS-версий у npm-пакетов нет. LTS есть у .NET (управляется через `global.json`) и у Node.js (`node-version: '22'` в workflow) — это разные уровни абстракции.
