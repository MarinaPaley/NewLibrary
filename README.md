# Шаблон репозитория: Разработка информационной системы

Стартовый шаблон для быстрой инициализации проектов на .NET 10 с настроенным контролем качества кода, автоматизацией и генерацией документации.

Этот репозиторий содержит готовую к использованию инфраструктуру: от правил статического анализа и pre-commit хуков до автоматического деплоя документации на GitHub Pages. Он позволяет сразу сосредоточиться на бизнес-логике, заменив шаблонные имена на названия вашей предметной области.


## Для чего этот репозиторий

Данный репозиторий является стартовым шаблоном (template) для быстрой инициализации новых проектов. Основное назначение — разработка информационной системы по теме, которую вы выберете при создании репозитория.

Шаблон включает в себя полностью настроенную инфраструктуру, строгие процессы обеспечения качества кода, автоматизацию проверок и генерацию документации. Это позволяет не тратить время на рутинную настройку окружения, а сразу приступить к реализации бизнес-логики.


## Технологический стек

- Платформа: .NET 10 (версия SDK зафиксирована в `global.json`), C# 14.
- Веб-фреймворк: ASP.NET Core Web API.
- Документирование API: Scalar (современная альтернатива Swagger UI).
- Тестирование: NUnit + coverlet (сборка покрытия кода).
- Контроль качества: единый стиль кода через `.editorconfig` и `dotnet format` (встроенное автоформатирование), анализаторы Meziantou, SonarAnalyzer, StyleCop.
- Документация и визуализация: Doxygen + Mermaid (`.mmd`) с автоматической публикацией на GitHub Pages.
- Орфография: CSpell с поддержкой русского, английского и технических словарей.
- Автоматизация: Husky.Net (pre-commit хуки), GitHub Actions (CI/CD), Central Package Management.


## Что установить локально

Для комфортной работы с шаблоном на вашей машине должны быть установлены:

1. Git — система контроля версий.
2. .NET SDK 10.x — версия подтянется автоматически из `global.json`.
3. Node.js 22.x (LTS) и npm — необходимы для работы CSpell, Mermaid CLI и Husky. Версия Node.js зафиксирована в workflow (`node-version: '22'`). На момент написания 22.x — действующая LTS-ветка. Более новые LTS (24.x, 26.x) также доступны; при обновлении шаблона проверьте актуальные версии на [официальном сайте Node.js](https://nodejs.org/).
4. IDE (Visual Studio 2026 / JetBrains Rider / VS Code) — с включенной поддержкой `.editorconfig`.

После клонирования репозитория выполните в корне:

#### 1. Восстановление NuGet-пакетов

~~~sh
dotnet restore
~~~

#### 2. Восстановление локальных инструментов .NET (Husky)

В корне репозитория лежит файл `dotnet-tools.json` — это локальный манифест инструментов .NET. В нём зафиксирована версия Husky.Net (0.9.1), которая нужна для работы pre-commit хуков. Команда `dotnet tool restore` читает этот манифест и устанавливает указанные в нём инструменты в локальное окружение проекта (без глобальной установки в систему). Благодаря этому версия Husky одинакова у всех разработчиков и в CI.
Команда `dotnet tool restore` только скачивает инструмент Husky из манифеста. Чтобы Git начал использовать хуки, нужен шаг 4 — `dotnet husky install`.
~~~sh
dotnet tool restore
~~~

#### 3. Установка зависимостей Node.js

~~~sh
npm install
~~~

#### 4. Активация pre-commit хуков

Выполните из **корня репозитория** (там, где лежат `.git` и `dotnet-tools.json`):

~~~sh
dotnet husky install
~~~

Если вы находитесь в `sources/`, поднимитесь на уровень выше командой `cd ..` — Husky ищет `.git` и манифест инструментов в одной папке и не устанавливается из подпапки.

После успешной установки вы увидите сообщение `Git hooks installed`, а файлы в `.husky/` обновятся. Папка `.git/hooks/` при этом останется нетронутой: Husky.Net не копирует туда скрипты, а настраивает Git на использование `.husky` через `core.hooksPath`. Это нормальное поведение — не пытайтесь искать изменения в `.git/hooks/`.

Без этого шага скачанный инструмент не активируется, и pre-commit хуки не сработают.

### Инструменты для документации и проверки орфографии

Эти инструменты **не обязательны** для запуска проекта. Они нужны только для локальной генерации документации и проверки орфографии.

**Doxygen** — генератор HTML-документации из исходного кода:

- Windows: скачайте установщик с [официального сайта](https://www.doxygen.nl/download.html)
- macOS: `brew install doxygen`
- Linux: `sudo apt-get install doxygen` (Ubuntu/Debian) или `sudo dnf install doxygen` (Fedora)

**Graphviz** — рендерит графы и диаграммы для Doxygen:

- Windows: скачайте установщик с [официального сайта](https://graphviz.org/download/)
- macOS: `brew install graphviz`
- Linux: `sudo apt-get install graphviz`

**CSpell и словари** — проверка орфографии в коде и документации.

CSpell и словари (`@cspell/dict-ru_ru`, `@cspell/dict-en_us`) уже перечислены в `package.json`. После шага 3 (`npm install`) они доступны локально, а `.cspell.json` подключает их автоматически. Запуск проверки из корня проекта:

~~~sh
npx cspell "**/*.{cs,md,json,yml,yaml}"
~~~

Если вы хотите запускать `cspell` из любого места без `npx`, установите CLI глобально:

~~~sh
npm install -g cspell
~~~

> **Примечание:** глобально ставится только CLI. Словари подхватываются из `node_modules` проекта через `.cspell.json`, поэтому команда `cspell link` **не нужна** — она предназначена для добавления словарей в глобальный пользовательский конфиг CSpell, а не в проектный [citation:2].

**Проверка орфографии в Visual Studio:**

Для проверки орфографии прямо в редакторе установите расширение [Visual Studio Spell Checker](https://marketplace.visualstudio.com/items?itemName=EWoodruff.VisualStudioSpellCheckerVS2022andLater). После установки оно автоматически подхватит пользовательские словари из папки `dics/` (`ru.txt`, `en.txt`, `tech.txt`).

> **Примечание:** Visual Studio Spell Checker и CSpell — это два разных инструмента. Spell Checker работает в IDE в реальном времени, а CSpell используется в CI/CD пайплайне для автоматической проверки. Оба инструмента используют одни и те же словари из папки `dics/`, что обеспечивает согласованность проверок.

**Проверка орфографии в VS Code:**

Если вы используете VS Code, установите расширение [Code Spell Checker](https://marketplace.visualstudio.com/items?itemName=streetsidesoftware.code-spell-checker). Оно автоматически подхватит конфигурацию из `.cspell.json` и словари из папки `dics/`.


## Как начать работу (Форк / Шаблон)

1. На странице этого репозитория нажмите кнопку `Use this template` -> `Create a new repository`.
2. Укажите имя нового репозитория и нажмите `Create repository`.
3. Склонируйте созданный репозиторий на свой компьютер:

~~~sh
git clone <url-вашего-репозитория>
~~~

4. Выполните первоначальную настройку окружения (см. раздел «Что установить локально»).

## Что изменить под себя (обязательно)

Поскольку это шаблон, в нескольких конфигурационных файлах жестко прописаны имена `Library`, `API` и `Domain`. Перед началом разработки их необходимо заменить на названия вашего проекта.

### 1. Переименование решения и проектов

- Переименуйте файл `sources/Library.slnx` в `sources/ВашеРешение.slnx`.
- Переименуйте папки проектов (`API`, `Domain`, `Domain.Tests`) и файлы `.csproj` внутри них под вашу предметную область.
- Обновите пространства имен (`namespace`) в файлах `.cs`.
- Обновите ссылки между проектами (например, в `Domain.Tests.csproj` путь к `Domain.csproj`).

### 2. Обновление конфигурационных файлов

После переименования обязательно откройте и исправьте следующие файлы:

- `task-runner.json`: в аргументах команды `format` замените `sources/Library.slnx` на `sources/ВашеРешение.slnx`.
- `.github/workflows/dotnet.yml`: в секции `env` замените `SOLUTION: Library.slnx` на `SOLUTION: ВашеРешение.slnx`. Обратите внимание: в `task-runner.json` путь указывается относительно корня репозитория (`sources/Library.slnx`), а в `dotnet.yml` — относительно `working-directory: sources` (`Library.slnx`). Это разные базовые директории, не перепутайте.
- `.github/workflows/docs.yml`: в секции `paths` замените пути к проектам (`sources/Domain/`, `sources/API/`) на пути к вашим новым проектам (иначе документация не будет пересобираться при их изменении). Полный список триггеров см. в разделе «Документация и GitHub Pages».
- `sources/_stylecop/stylecop.json`: при необходимости обновите `copyrightText`.
- `docs/Doxyfile`: замените `PROJECT_NAME` на название вашего проекта.
- `.cspell.json`: секция `files` должна соответствовать путям, по которым CSpell ищет файлы. Если вы переименовали проекты (например, `Domain` → `YourDomain`), обновите пути в `files`. Обратите внимание: `docs.yml` в секции `paths` триггерит сборку по одним путям (например, `sources/API/**`), а CSpell в `files` может проверять другие (например, только `sources/Domain/**/*.cs`).

### 3. Адаптация словарей

- `dics/` — пользовательские словари. Дополняйте их терминами вашей предметной области по мере необходимости. Шаблонные словари уже содержат базовый набор русских, английских и технических слов — их можно оставить и расширять, а не заменять целиком.


## Использование

После адаптации шаблон полностью готов к работе:

- Любая попытка сделать коммит с неформатированным кодом будет автоматически отклонена хуком `dotnet format`.
- При пуше в ветку `master` автоматически запускается сборка, тесты и проверка стиля (файл `.github/workflows/dotnet.yml`).
- При изменении кода или документации автоматически генерируется и публикуется сайт с документацией (файл `.github/workflows/docs.yml`).

### Настройка GitHub Pages (сделать один раз)

1. Перейти в Settings -> Pages -> Build and deployment.
2. В поле Source выбрать GitHub Actions.
3. **Проверить ветку деплоя.** Перейти в Settings -> Environments -> `github-pages` -> Deployment branches and tags. По умолчанию GitHub может разрешить деплой только с ветки `main`, даже если ваш workflow пушится в `master`. Если в правиле указана не та ветка — добавьте `master` (или выберите «No restriction»). Без этого шага деплой упадёт с ошибкой `Branch "master" is not allowed to deploy to github-pages`.
4. Остальное создастся автоматически при первом успешном запуске workflow.

URL сайта будет виден в логах шага Deploy to GitHub Pages (формат: `https://<owner>.github.io/<repository>/`).

### Окончания строк

Файл `.gitattributes` жестко предписывает использовать окончания строк `LF` для всех текстовых файлов. Рекомендуемая настройка клиента Git: `git config --global core.autocrlf false`.


## Контроль качества кода

В проекте выстроена строгая культура написания кода. Все проверки запускаются автоматически.

### Локально (pre-commit хуки)

Перед каждым коммитом Husky.Net запускает задачу из `.husky/task-runner.json`:

~~~text
dotnet format sources/ВашеРешение.slnx --verify-no-changes
~~~

Флаг `--verify-no-changes` означает, что хук **не форматирует файлы**, а только **проверяет**, что они уже отформатированы. Это осознанный выбор в пользу предсказуемости: хук не меняет файлы «за спиной» и не создаёт рассинхронизацию между индексом и рабочей директорией. Если бы хук форматировал файлы сам, возникала бы ситуация, когда коммит уходит со старым содержимым, а исправленный файл остаётся в рабочей директории и требует второго коммита.

Если код не соответствует `.editorconfig`, хук завершается с ошибкой и **отклоняет коммит**. В этом случае:

1. Запустите форматирование вручную:
   ~~~sh
   dotnet format sources/ВашеРешение.slnx
   ~~~
2. Добавьте исправленные файлы в индекс (`git add`) и повторите коммит.

После этого коммит пройдёт, и в нём будет уже отформатированный код. Отдельно устанавливать `dotnet format` не нужно — это встроенная команда SDK, её версия привязана к версии SDK из `global.json`.

Такое поведение полностью совпадает с проверкой в CI: шаг `dotnet format --verify-no-changes` в `dotnet.yml` делает то же самое. Локальный хук — это раннее предупреждение, а CI — финальная проверка.

### В CI (GitHub Actions)

Все проверки дублируются в пайплайне `.github/workflows/dotnet.yml`:

- Восстановление локальных инструментов (`dotnet tool restore`).
- Проверка формата кода (`dotnet format --verify-no-changes`).
- Восстановление зависимостей (`dotnet restore`).
- Сборка решения в режиме Release.
- Запуск тестов с генерацией покрытия.

### Статический анализ

Используется многоуровневая система анализаторов:

- `Directory.Build.props` (в корне) — включает .NET анализаторы, устанавливает уровень `latest-recommended`, принудительно применяет стиль кода при сборке, генерирует XML-документацию для Swagger/Scalar.
- `.editorconfig` (в корне) — строгие правила стиля: обязательное использование `this.`, `var` только для встроенных типов, `using` внутри namespace, фигурные скобки в стиле Allman, приватные поля в camelCase без подчеркивания.
- `.globalconfig` — глобальные переопределения серьезности конкретных диагностик (например, отключение предупреждений о локализации, упрощении коллекций, именовании).
- `sources/_stylecop/develop.ruleset` — набор правил StyleCop для основного кода.

**Важно:** `TreatWarningsAsErrors` в корневом `Directory.Build.props` **закомментирован** — предупреждения анализаторов показываются, но не ломают сборку. Это сделано осознанно: шаблон должен запускаться «из коробки» даже на небольшом проекте, где много предупреждений на старте. По мере взросления проекта можно раскомментировать эту строку и постепенно исправлять предупреждения, чтобы они не накапливались. В тестах `TreatWarningsAsErrors` всегда `false` (см. `sources/tests/Directory.Build.props`), чтобы предупреждения не отвлекали от сути тестов.

### Особенности для тестов

К тестам применяются ослабленные требования, чтобы не отвлекать разработчиков от сути тестов. Это реализовано через два файла в папке `sources/tests/`:

- `tests/Directory.Build.props` — импортирует корневой `Directory.Build.props`, но переопределяет:
  - `IsTestProject = true`
  - `TreatWarningsAsErrors = false`
  - `GenerateDocumentationFile = false` (XML-документация в тестах не нужна)
  - Использует `tests.ruleset` вместо `develop.ruleset`
- `tests/.editorconfig` — переопределяет правила только для тестов: отключает правило CA1707, разрешая подчёркивания в именах методов (например, `Should_Return_True`). Все остальные правила стиля наследуются из корневого `.editorconfig`.

`TreatWarningsAsErrors = false` в тестах отключает **анализаторы как ошибки сборки** (например, CA1707 про подчёркивания не валит `dotnet build`). Однако это **не отключает** проверку форматирования в CI: шаг `dotnet format --verify-no-changes` в `dotnet.yml` проверяет стиль для всех проектов, включая тесты. Именно поэтому в `tests/.editorconfig` точечно отключено правило CA1707 — иначе `dotnet format` считал бы `Should_Return_True` нарушением стиля. Остальные правила стиля для тестов наследуются из корневого `.editorconfig`.

Благодаря этому тесты остаются читаемыми и не загромождаются лишней документацией, а основной код сохраняет строгий стиль.


## Документация и GitHub Pages

Документация генерируется через Doxygen и публикуется на GitHub Pages автоматически через workflow `.github/workflows/docs.yml`.

### Когда запускается сборка

Workflow срабатывает только в трёх случаях:

1. Push или merge в `master`, если изменились файлы из списка: `sources/Domain/`, `sources/API/`, `docs/`, `dics/`, `.cspell.json`, `.github/workflows/docs.yml`, `package.json`.
2. Публикация GitHub Release.
3. Вручную через кнопку Run workflow во вкладке Actions.

Важно: отдельных триггеров на `pull_request` нет. При открытии или обновлении PR документация не публикуется. Сборка происходит только после merge в `master`.

### Проверка орфографии (CSpell)

Перед генерацией запускается проверка орфографии. Для гарантированной работы словарей в CI:

- Устанавливаются пакеты, указанные в `package.json` (включая `@cspell/dict-ru_ru` и `@cspell/dict-en_us`).
- Конфигурация берётся из `.cspell.json`, который подключает стандартные словари (`ru-ru`, `en-us`, `russian`, `english`) и пользовательские словари из папки `dics/` (в `.cspell.json` они зарегистрированы как `project-ru`, `project-en`, `project-tech` — это имена словарей, а не имена файлов; файлы называются `ru.txt`, `en.txt`, `tech.txt`).


## Как обновлять версии

### Обновление .NET и NuGet-пакетов

- Версия SDK: измените номер в `global.json`.
- Версии пакетов: измените версии в `Directory.Packages.props`. Благодаря Central Package Management, вам не нужно менять версии в каждом `.csproj` файле.

### Обновление Node.js зависимостей (CSpell, Mermaid)

Версии инструментов зафиксированы в корневом `package.json` с использованием символа `^` (caret):

~~~json
{
  "devDependencies": {
    "cspell": "^8.0.0",
    "@mermaid-js/mermaid-cli": "^10.9.0",
    "@cspell/dict-ru_ru": "^2.0.0",
    "@cspell/dict-en_us": "^4.0.0"
  }
}
~~~

Правило `^`:

- Патчи (8.0.1) и минорные (8.1.0) версии подхватываются автоматически при `npm install`.
- Мажорные (9.0.0) версии не подхватываются, что защищает сборку от внезапных поломок API.

Файл `package-lock.json` не коммитится (добавлен в `.gitignore` вместе с `node_modules/`). В workflow намеренно отключен `cache: 'npm'`, чтобы зависимости устанавливались чисто и предсказуемо при каждом запуске.

#### Как обновить мажорную версию вручную

1. В `package.json` поменяйте версию, например: `"cspell": "^9.0.0"`.
2. Закоммитьте изменение и оформите PR в `master`.
3. После merge workflow соберёт документацию с новой версией (изменение `package.json` есть в триггерах).

Примечание: LTS-версий у npm-пакетов нет. `global.json` фиксирует версию SDK, а LTS — это характеристика самого релиза .NET. Версия Node.js фиксируется отдельно в workflow (`node-version: '22'`) — это независимые уровни абстракции.
